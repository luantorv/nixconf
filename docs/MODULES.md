# Modules and Importing

This document explains how modules are organized and imported in this repository: which file loads what, in what order, and how `specialArgs` (`globalVars`, `pkgs-old`, `pkgs-new`, etc.) flow from `flake.nix` to the most specific module.

## Overview

```
flake.nix
  └── hosts/<machine>/default.nix     # hardware + selects ONE profile
        └── profiles/<profile>.nix    # assembles NixOS + Home Manager modules
              ├── modules/nixos/...   # system-level configuration
              └── modules/home/...    # user-level configuration
```

Each layer imports only downward: a host does not know what is inside a module, and a profile does not know what hardware the host has. This makes it possible to reuse the same profile (`river.nix`, `plasma.nix`, `minimal.nix`) on different machines.

## 1. `flake.nix` — the single entry point

`flake.nix` does three things:

1. **Declares the `inputs`**: `nixpkgs` (26.05, main version), `nixpkgs-old` (25.11), and `nixpkgs-new` (unstable), plus `home-manager`, `sops-nix`, `plasma-manager`, and `nix-cachyos-kernel`.
2. **Defines `globalVars`**: an attrset with `username`, `homeDirectory`, `system`, `stateVersion`, wallpaper paths, etc. It is the single source of truth for these values; no module should hardcode them.
3. **Builds `nixosConfigurations.<host>`** (`laptop`, `server`), passing `globalVars` and the relevant flake inputs as `specialArgs`, and importing `home-manager.nixosModules.home-manager`, `sops-nix.nixosModules.sops`, and `./hosts/<host>/default.nix`.

`pkgs-old` and `pkgs-new` are instantiated only once in the `let` block of `flake.nix` (with `allowUnfree = true`) and injected as `specialArgs` so that any module, at any layer, can use a package from a different nixpkgs version without reinstantiating anything.

Note that `laptop` receives `plasma-manager` in its `specialArgs`, while `server` does not — because `server` does not use a graphical profile that needs them.

## 2. `hosts/<machine>/default.nix` — hardware + profile selection

Each host (`laptop`, `server`) has its own directory with:

- `hardware-configuration.nix` — generated by `nixos-generate-config`, not edited by hand.
- `hardware.nix`, `boot.nix`, `docker.nix` — machine-specific configuration.
- `default.nix` — the module that ties everything together **and imports exactly one profile** from `../../profiles/`.

Example (`hosts/laptop/default.nix`):

```nix
imports = [
  ./hardware-configuration.nix
  ./boot.nix
  ./hardware.nix
  ./docker.nix
  ../../modules/home/sops.nix
  ../../modules/nixos/cachyos-kernel.nix
  ../../profiles/plasma.nix          # <- profile selection
];
```

This is also where the `home-manager = { ... }` block is configured at the host level: `useUserPackages`, `extraSpecialArgs` (forwards `globalVars`, `sops-nix`, `pkgs-old`, `pkgs-new`... to Home Manager modules), `sharedModules` (to inject `sops-nix.homeManagerModules.sops` or `plasma-manager.homeModules.plasma-manager`), and `backupFileExtension = "backup"` (so Home Manager does not fail if unmanaged dotfiles already exist).

`hosts/server/default.nix` follows the same pattern but imports `../../profiles/minimal.nix` and `../../modules/nixos/server.nix`, and does not receive `pkgs-new`/`plasma-manager` because it does not need them.

## 3. `profiles/*.nix` — NixOS + Home Manager assembly

A profile is the module “menu” for a use case. There are three:

| Profile | Desktop | Use |
|---|---|---|
| `minimal.nix` | none (TTY) | servers, pure CLI/TUI |
| `river.nix` | River (Wayland WM) | laptop with a minimal WM |
| `plasma.nix` | KDE Plasma | laptop with a full DE |

Each profile has two separate `imports` blocks:

```nix
{
  imports = [                        # <- NixOS modules (system)
    ../modules/nixos/core
    ../modules/nixos/packages.nix
    ...
  ];

  home-manager.users.${globalVars.username} = { pkgs, pkgs-old, ... }: {
    imports = [                      # <- Home Manager modules (user)
      ../modules/home/packages/river.nix
      ../modules/home/river
      ...
    ];

    home = {
      inherit (globalVars) username homeDirectory;
    };
  };
}
```

- The first `imports` (at the module root level) is pure NixOS: only `nixpkgs.lib.nixosSystem` sees it.
- The second lives inside `home-manager.users.${globalVars.username} = { ... }: { ... }`, which is a **Home Manager module function**: it receives its own arguments (`pkgs`, `pkgs-old`, etc., defined by `extraSpecialArgs` in the host) independently from those of the surrounding NixOS module.

`modules/nixos/core` (see below) is imported in **all** graphical profiles (`river.nix`, `plasma.nix`); `minimal.nix` imports `core/base.nix` and `core/nix.nix` directly instead of the full `core/` aggregator, because it does not need `core/networking.nix` with graphical NetworkManager (it uses systemd-networkd/minimal setup).

## 4. `modules/nixos/` and `modules/home/` — the aggregator `default.nix` pattern

Inside `modules/`, each subfolder with several related files has a `default.nix` that simply reimports them:

```nix
# modules/nixos/core/default.nix
{
  imports = [
    ./base.nix
    ./networking.nix
    ./nix.nix
  ];
}
```

```nix
# modules/home/theme/default.nix
{
  imports = [
    ./colors.nix
    ./wallpapers.nix
  ];
}
```

This lets a profile import the whole folder (`../modules/home/theme`) without listing each file, and adding a new `.nix` file to that folder only requires changing its own `default.nix`, not every profile that uses it.

Folders that follow this pattern: `modules/nixos/core/`, `modules/home/desktop/`, `modules/home/editors/`, `modules/home/files/`, `modules/home/plasma/`, `modules/home/river/`, `modules/home/shell/`, `modules/home/terminal/`, `modules/home/theme/`.

Loose files (without an aggregator folder) are imported directly by full path from the profile or host, e.g. `modules/home/sops.nix`, `modules/home/cliphist.nix`, `modules/home/variables.nix`, `modules/nixos/packages.nix`, `modules/nixos/services.nix`, `modules/nixos/security.nix`, `modules/nixos/users.nix`, `modules/nixos/variables.nix`, `modules/nixos/android.nix`.

### `modules/home/packages/`

Special case: it does not have an aggregator `default.nix` because each file is an **alternative package list** for a profile tier (`minimal.nix`, `river.nix`, `plasma.nix`, `desktop.nix`), not a set that should be combined. Each profile imports only the file that corresponds to it (for example, `river.nix` imports `../modules/home/packages/river.nix`).

## 5. `specialArgs` / `extraSpecialArgs` flow

| Argument | Defined in | Repassed to | Typical use |
|---|---|---|---|
| `globalVars` | `flake.nix` (`let`) | `specialArgs` (NixOS) and `extraSpecialArgs` (Home Manager) in each host | username, home, wallpapers, `stateVersion` |
| `pkgs-old` / `pkgs-new` | `flake.nix` (`let`, `import nixpkgs-old/new { ... }`) | same as above | packages that need another nixpkgs version |
| `sops-nix`, `plasma-manager`, `nix-cachyos-kernel` | flake `inputs` | host `specialArgs` that need them | modules/`homeModules` from those flakes |

Key points:

- **No NixOS module automatically sees Home Manager arguments**, and vice versa: the `home-manager.users.<user> = { ... }: { ... }` block in each profile is a separate module function, whose available arguments depend on what the host put in `home-manager.extraSpecialArgs`.
- If a new module needs `pkgs-new` (for example), first make sure the corresponding host includes it in `specialArgs`/`extraSpecialArgs` — `server` currently does not have it, `laptop` does.
- `globalVars` is never redefined outside `flake.nix`; all modules receive it as an argument and destructure it (`{ globalVars, ... }:`), never import it another way.

## 6. Adding a new module — checklist

1. Create the `.nix` file in `modules/nixos/` or `modules/home/<category>/`.
2. If the category has an aggregator `default.nix`, add it to its `imports` list. If not, add the path directly in the profile(s) that should use it.
3. If the module needs an argument it does not receive yet (`pkgs-old`, a new flake input, etc.), add it to the module function signature (`{ config, pkgs, globalVars, ... }:`) and verify that it is present in the host’s `specialArgs`/`extraSpecialArgs`.
4. Test with `sudo nixos-rebuild build --flake .#<host>` before `switch`.
